# PackGuard mode test sets

Two large, mixed-provenance test sets for the two stage-1 modes. Each set contains
both **downloaded** packages and **invented** packages, and each is labelled by the
categories the corresponding mode claims to cover.

| Set | Mode | What it measures |
|---|---|---|
| `known/` | `packguard --mode known` (v6) | Renamed and mangled known families: raw known packages, new versions, new names, T1–T4 transforms, install scripts, base64/hex payloads |
| `new/` | `packguard --mode new` | New campaigns whose family is not in the references: new code shapes, streamed clones, behavioural primitives, install-script attacks, encoded loaders |

The plaintext sets were built on the GCE instance and deleted after the encrypted
export on 2026-11-07. The encrypted archives now live in `data/from-instance/`
(password `infected`); the repository keeps those archives, the generators, the
manifests and the summaries, while the generated sample folders are ignored by
`.gitignore`.

## Provenance types

| Type | Folder | Source |
|---|---|---|
| Downloaded | `*/real/` | DataDog `malicious_intent` samples (live malware) and the shipped v1/v2 corpora |
| Invented | `*/invented/` | Generated by `scripts/generate_invented.py`: mangled variants of real families plus fully authored malware-style packages |

The invented packages are **inert**: every endpoint is under `.invalid`, credentials
and wallet paths are dummy, and no command is destructive or persistent. They are
written to look like real npm packages (`package.json`, install hooks, multiple
files) so the scanner must treat them as targets, not as reference material.

## Built sets (2026-11-06)

Built on the GCE instance with `./run_server.sh` (`DERIVED=600`, `PER_CATEGORY=300`,
`KNOWN_REAL=1200`). The instance holds 20,135 packages, about 391 MiB of plaintext
sample files plus a 215 MiB DataDog download cache.

| Set | Kind | Packages |
|---|---|---|
| `known` | real | 4,200 |
| `known` | invented | 6,850 |
| `new` | real | 1,885 |
| `new` | invented | 7,200 |
| **Total** | | **20,135** |

Known set: `mal_known` 720, `mal_newver` 500, `mal_newname` 2,500, `mal_scripts`
480, T1–T4 530 each, `payload_base64` 265, `payload_hex` 265, and 600 each of
`install_scripts`, `typosquat`, `dropper`, `stealer`, `padded_loader`,
`encoded_loader` and `multi_stage`.

New set: `mal_shape` 285, `mal_stream` 900, `mal_scripts` 300, `mal_encoded` 400,
plus 300 each of the 24 invented categories listed above.

The authored packages in the known set are novel code. Known mode relies on
similarity to the references, so it may miss them even though every one carries the
behavioural primitives the new mode looks for; they mark the boundary between the
two modes. The mangled `T1`–`T4` and payload folders are the known-mode samples that
retain the family code.

Ten to twenty packages per category, not the full 20,135, from the reports in
`report_stats.json`.

| Mode | Category | Flagged |
|---|---|---|
| known | `T1_format` / `T2_rename` / `T3_padding` / `T4_base64` | 10/10 each |
| known | `mal_known` | 10/10 |
| known | `mal_newname` | 9/10 |
| known | `mal_newver` | 125/200 |
| known | `mal_scripts` | 20/20 |
| new | `mal_shape` / `mal_stream` / `mal_scripts` / `mal_encoded` | 20/20 each |

The `mal_newver` gap is real: those versions often moved their attack into an
install script with a new endpoint, so the old version in the references no longer
matches. The new mode's primitive channel is the path for them; run `--mode new`
over the same packages.

## Build on the GCE instance

```bash
cd ~/packguard/test-sets/scripts
./run_server.sh
```

`run_server.sh` runs `generate_invented.py` and `build_real.py`, then writes
`stats.json`. The DataDog download is incremental: zips already in `cache/datadog/`
are kept. Pass `--skip-download` to build only from the corpora already on the
instance.

Useful overrides:

```bash
DERIVED=600 PER_CATEGORY=300 KNOWN_REAL=1200 ./run_server.sh
THREADS=64 ./run_server.sh
```

`build_real.py --pack` also writes one encrypted zip per category under
`~/pg-test-sets/zips/`, so the plaintext set can be archived or copied without
ever writing live malware to a Windows disk.

## Scan

```bash
cd ~/packguard/test-sets/scripts
./scan_sets.sh known
./scan_sets.sh new
LIMIT=20 ./scan_sets.sh known      # a quick sample per category
```

The scanner is run category by category so the argument list stays small. Known
mode uses the benign veto `-B ~/packguard-data/v7/benign_refs`; new mode does not.
Reports land in `~/pg-test-sets/reports/<set>/<kind>/<category>/` and the script
prints a per-category table.

## Safety

- `known/real` and `new/real` are live malware. They are only materialized on the
  isolated GCE instance and are excluded from git.
- The invented packages are inert by construction. Even so, a Windows antivirus
  may quarantine files that contain reverse-shell or `curl | sh` text; that is why
  the build runs on the instance and not on Windows.
- Only encrypted archives (`password infected`) may leave the instance.
- The repository commits no extracted sample, only the generators, manifests and
  summaries.
